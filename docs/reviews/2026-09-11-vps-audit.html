01

Incident, first

What happened

Probing PUT /api/config with {"field": null}, expecting a rejection. It applied. In about one second the live tenant lost business_name, persona, tone, custom_instructions (1,821 characters of grounding rules) and payment_details — while the rep was switched on and answering customers.

Restored from values captured in an earlier session, verified field by field. Exposure was roughly forty seconds. Any customer who wrote in that window got a reply from a rep with no business name, no persona and no rules.

My mistake was assuming a rejection. The reason it is finding C1 rather than a footnote is that nothing in the system resisted, warned, recorded what was lost, or offered a way back — and the same request is one serialiser default away from arriving by accident.

02

Backend, API and error handling

A battery of roughly sixty requests: authentication edge cases, malformed and hostile input, unicode, payload size, HTTP semantics, pagination bounds, CORS, cross-tenant access, concurrency and rate limits. Most of it came back correct. What did not is below.

C1
Critical

One PUT erases a tenant's entire AI configuration, returns 200, and leaves no way back.

Nine fields, three different behaviours for the same operation:

{"persona":null}              -> 200  applied, field erased
{"tone":null}                 -> 200  applied, field erased
{"custom_instructions":null}  -> 200  applied, field erased
{"business_name":null}        -> 200  applied, field erased
{"payment_details":null}      -> 200  applied, field erased
{"reply_language":null}       -> 200  applied
{"voice_reply_mode":null}     -> 200  applied
{"primary_language":null}     -> 500  Internal Server Error
{"timezone":null}             -> 500  Internal Server Error

Three things make this worse than a validation gap.

Null is what "unset" looks like on the wire. Most JSON serialisers, most form libraries and most typed clients emit null for an absent optional. A partner integration, a future mobile client or a retry of a partially-filled form erases the business's rules and is told it succeeded.

Unknown fields are accepted silently. {"totally_unknown_field":"x"} returns 200 with the config body. So a misspelled field name reports success and changes nothing, while a correct one reports success and destroys everything. The caller cannot distinguish them.

The audit log records it and cannot help. All five writes appear, correctly attributed and timestamped — as config_updated, with no field list and no before-and-after. You can see that something erased the tenant's brain and you cannot see what, or restore it.

FixReject null on a partial update, or require an explicit sentinel to clear a field. Set extra="forbid" so a typo is a 422. Handle the two crashers. Record changed field names in the audit row. And give the tenant's configuration a history with restore — it is the most valuable thing in the account and it is the only thing with no undo.

H1
High

The NUL-byte bug is not fixed. It moved from a silent crash to a 500.

POST /api/knowledge/sources
{"type":"manual","title":"QA nul","content":"before\x00after"}
-> 500 Internal Server Error

Last round this arrived as a worker crash that left a PDF stuck on "Processing" forever. The same unsanitised byte now reaches the database through the API boundary instead. Nothing strips \x00 anywhere on the path, so any text containing one — and PDF extraction produces them routinely — still fails, just louder.

FixStrip control characters at the model validator, once, so every entry point inherits it.

H2
High

A double-click on "Send invite" breaks the seat entitlement.

Two identical invitations fired concurrently. Both returned 201. The plan allows two seats:

seats: used 3 of 2 | state: over | remaining: 0
third invite -> 402 "No seats left on your plan."

The check is read-then-write with no lock and no unique constraint, so the window between counting and inserting admits an extra seat. The gate then correctly refuses the next one, which caps the damage at one seat per race — but on a fifteen-seat plan an impatient user can repeat it, and this is exactly the shape a double submit takes.

FixA unique index on (tenant, email, pending) and the count inside the transaction.

M1
Medium

An 8 MB request body is fully read and parsed before being rejected.

The 50,000-character cap is enforced by a field validator, which runs after the body is buffered and deserialised. The rejection is correct; the work done to reach it is not bounded. There is no request-size limit at the proxy or the app.

FixA body-size limit in Caddy, well above any legitimate request and well below what makes memory interesting.

M2
Medium

A knowledge source can be created with an empty title.

{"type":"manual","title":"","content":"x"} returns 201. content has a length rule and title has only "required", so an empty string passes and the sources table renders a blank row that cannot be identified.

L1
Low

Three small perimeter details.

server: uvicorn on every API response names the software and rough version class for free. A 429 carries no Retry-After, so a well-behaved client has to guess. And the public landing page is served cache-control: private, no-cache, no-store while setting two auth cookies for anonymous visitors — the marketing page cannot be cached by anything, and it is the page that most wants to be.

03

Visual and UX

The interface has moved a long way. Grouped navigation, a real design system with enforced tokens, honest empty states, and copy that reads like a person wrote it for a salon owner rather than for a developer. Two things are wrong, one of them badly.

H3
High

Three pages scroll sideways on a phone, and the header controls scroll off with them.

At a 390-pixel viewport:

/knowledge  document width 922px   (2.4x the screen)
/billing    document width 514px
/analytics  document width 436px
/inbox      document width 390px   correct

On Knowledge the rep on/off switch, the notification bell and the avatar are all off-screen to the right, the drop zone text is cut mid-word, and every usage meter runs past the edge. The page is unusable without panning.

The cause is one thing in three places. The tables do sit in overflow-x: auto wrappers — that part is right. But the flex column above them (flex flex-1 flex-col → main) has no min-w-0, so under flexbox's min-width: auto the scroll container is never constrained to the viewport and simply grows to its content. The wrapper is correct and inert.

table  min-width: 760px, actual 888px
parent overflow-x: auto  but itself 888px wide
grandparent overflow: hidden at 890px, inside an unbounded flex column

This is the same family as the inbox height bug from the first review: a container that cannot do its job because an ancestor never gave it a size.

Fixmin-w-0 on the flex column and on main. One change, three pages, and it inoculates every future table.

H4
High

Two people editing the same settings silently overwrite each other.

Two simultaneous PUT /api/config with different values:

tone before: "Warm, Concise, Direct"
PUT {"tone":"RACE-AAA"}  -> 200
PUT {"tone":"RACE-BBB"}  -> 200      (both accepted)
tone after : "RACE-BBB"             last write wins, silently

There is no ETag, no If-Match and no version column, so the API cannot tell a fresh edit from one made against a stale copy. An owner and a staff member both on Behavior, or one person with the page open in two tabs, and one of them loses their work with a success message.

It is the same soft spot as C1: this endpoint accepts whatever it is handed and reports success. Configuration is the tenant's most valuable asset and it has neither concurrency control nor history.

FixReturn a version with the config and require it on write, rejecting a stale one with a 409. The same version makes an undo possible.

R1
Retraction

I reported notifications as broken. They are not. They are one of the better parts of the product.

My first measurement read a read_at field that does not exist — the field is read — so every row looked unread and the badge looked stuck. Measured correctly:

before opening the panel : 4 unread, 2 of them stale
header badge            : 2          matches unread-and-not-stale exactly
after opening the panel : 0 unread   the panel marks them read
POST /notifications/{id}/read -> 200, row flips to read: true

The badge is not a raw unread count: it deliberately excludes notices the system has since invalidated. And the invalidation is the part worth calling out, because it is the fix recommended in the previous review, implemented more thoroughly than asked. The two stale voice notices are struck through in the panel and carry their own explanation:

"No longer applies. Voice was re-measured after this was sent: your rep
 has used 3 of 5 voice minutes this month (172 of 300 seconds), so voice
 replies were never paused and have kept working."

A product that goes back and corrects something it told you, in the place it told you, is rare. I was wrong about this one.

What is working, as a piece of product design

G1
Excellent

"Improve with AI" is the best thing in the product.

It states what it looks for before you press it — rules that fight your settings, rules that switch off a connected tool, promises made on your behalf, vague duplicates you pay for on every reply. It says plainly that it costs one call to your own provider and only runs on press. It renders a side-by-side diff, explains each change with a reason, shows the resulting character count, and needs two deliberate actions to apply.

Run against the live instructions it found, unprompted, the exact three defects diagnosed by hand in the previous review: the diary lines that contradict a connected Google Calendar, the language rules that duplicate and override the Reply language setting, and the "a representative will call within a few hours" promise. A one-off fix became a feature that keeps finding the problem.

G2
Good

The interface now explains itself where it used to just work.

Skills marks a capability whose own instructions contradict it, quotes the offending line, links to the fix, and adds "this is a keyword check, not a reading of your instructions, so it can be wrong" — a product admitting the limits of its own inference. The Devices card says why there is no device list rather than showing an empty one. Billing explains that the usage reset date and the renewal date are different things and why. The knowledge caps say what happens when each one fills. Almost none of this existed two reviews ago.

Smaller UX observations

  • Analytics contradicts itself at a glance. "NEEDS HUMAN NOW 0" sits beside "OPEN HANDOFFS 1". Both are true and they read as a bug.
  • Greetings still dominate knowledge gaps. "Hi ×2", "Hello how are you doing?" and "Hi Bye Hi" are three of the top five, under a prominent "Answer these in Knowledge" call to action. The product is inviting the owner to write knowledge articles about the word hello.
  • The inbox empty state is 640 pixels of dashed box. Opening the most recent conversation by default would be more useful than asking the reader to pick one.
  • Both inbox panes have identical weight — same fill, border and radius — so the transcript, which is the object of the screen, reads as equal to the list.
  • "Link another number" floats outside its card with no button affordance, reading as unstyled text.
  • Casing drifts in the admin tables: status chips are lowercase (active) beside capitalised plans (Trial, Starter).
04

Features and the ops console

M3
Medium

System Health forgets everything on every deploy.

MESSAGES PROCESSED 5 · REPLIES SENT 3 · AVG TURN LATENCY 4.88s
Provider errors 0 · Job failures 0 · Webhook 401s 0 · Skill invocations: none

Those are process-lifetime counters, and the VPS migration restarted everything, so the page reports a system that has barely run. Two days ago the same page showed six provider errors and two job failures — the two dropped customer messages from the last review. That history is gone, and now that deploys are automated on every release tag it will be gone regularly. A page called System Health that cannot show yesterday is a page you cannot investigate with.

FixLabel them as since-restart and show the restart time, then point the real questions at the Prometheus series that already exists behind them.

M4
Medium

Admin two-factor shipped, and the admin account has not enrolled.

The feature is built and enrolls by QR. The account that can impersonate any owner, delete any tenant and read the whole fleet signed in today with a password alone, from the public internet, with no prompt. A control nobody turned on is not a control.

FixEnrol now, then require it for the qonvo_admin role rather than offering it.

M5
Medium

A customer's number has been down for three days, and the alerting that exists does not reach you.

Fleet Health has shown Husain bh Ezzy — UNREACHABLE (stored: FAILED) since the first review. The good news is that session alerts now exist: this tenant's own notification list contains "Your WhatsApp number stopped replying" and "Your WhatsApp number is back online". So the owner is told, in the app.

What is missing is the operator's half. Nothing emails, nothing pages, and the admin console has no notification surface of its own — you learn about a dead customer by choosing to look. Three days is the measurement.

FixSend the owner an email as well as an in-app notice, and give the console a digest of anything unreachable for more than an hour.

L2
Low

The documented knowledge source type no longer exists.

docs/FEATURES.md describes type: "text" and type: "url" mapping onto website. The API now accepts only manual, file, url, and a text request 422s. Harmless internally, and it is the first thing an integrator would hit.

07

End to end, both environments

Staging runs locally, so the destructive half went there: signup, verification, the authorization matrix, the pipeline gates and a signed webhook straight into the ingress. Production took the reversible half. Four more defects, and a long list of things that turned out to work properly.

New defects

H5
High

A double-tap on the rep switch can leave the rep off while the screen says it is on.

PUT /api/activation {"rep_active": false}   -> 200
PUT /api/activation {"rep_active": true}    -> 200   (fired together)
GET /api/activation                         -> rep_active: false

Same last-write-wins as the config endpoint, but the consequence is worse: the losing write is the one the interface believes it made, so the toggle reads Rep on while the rep is off and every customer message goes unanswered. Nothing reconciles the two, and the failure is invisible until somebody notices the silence.

FixDisable the control while a change is in flight, and have the response drive the displayed state rather than the optimistic value.

M6
Medium

WhatsApp sessions can be created without limit and cannot be deleted at all.

Eight rapid creates, eight 201s, eleven sessions on one tenant. Then:

DELETE /api/sessions/{name}  -> 404   (the route does not exist)
openapi.json session routes  : GET,POST /api/sessions
                               POST .../logout, .../restart
                               GET  .../qr, .../status

There is logout and restart, and no removal. The plan entitlements name messages, voice, seats, sources, characters and bytes, and say nothing about numbers, so nothing bounds this. Creation only writes a row rather than provisioning an engine immediately, which keeps it out of the critical band, but the WhatsApp page will accumulate rows a tenant can never tidy — and multiple numbers is on your own price list as a paid feature.

FixAn entitlement for numbers, and a delete that logs out and removes the row.

M7
Medium

The add-website dialog throws away a good error and shows nothing.

Entering a private address is correctly refused by the API, with a message written for a human:

POST /api/knowledge/sources {"type":"url","url":"http://169.254.169.254/..."}
-> 400 {"detail":"that address points inside a private network,
         so it cannot be reached"}

In the interface the dialog simply stays open. No message, no inline error, no toast. The owner presses "Add website", nothing happens, and the reason the server took the trouble to explain is discarded.

FixRender detail in the dialog. The hard half is already done.

M8
Medium

seed_dev.py prints a password it did not set.

The script creates the dev owner and admin only when they are missing, then unconditionally prints OWNER_PASSWORD=dev-password-123. On an existing user it reports a credential that does not work — which is exactly how it was found, by not being able to log in with it. CLAUDE.md documents re-running it as the recovery route for a locked-out admin, and that route does nothing.

FixReset the hash on an existing user, or print what actually happened. Then correct the runbook.

L3
Low

Three contract details.

POST /api/billing/change-plan answers 200 {"ok": false, "reason": "no_subscription"}. A client checking the status code believes the plan changed. Same for resume.

POST /api/billing/cancel requires a body and rejects an empty call with 422 {"loc": ["body"], "msg": "Field required"}, which does not say which field.

Staff can read GET /api/billing — plan, status, entitlements, provider and period end — while /api/billing/payments correctly answers 403. One boundary, two answers.

last_ingested is written for new ingests but was never backfilled, so the two long-standing sources still read Never while a fresh one reads just now.

The theme, third time

The first review found missing features. The second found things that fail without telling anyone. This one found something narrower and more useful: the product is now good at explaining itself and still bad at protecting itself. It will tell an owner why a skill is disabled, what a meter means, which instruction contradicts which integration — and it will let one malformed request erase the configuration behind all of it and answer 200. The interface has grown a conscience faster than the API has grown a guard rail.
